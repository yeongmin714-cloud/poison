# 영지별 실내 레이아웃 다양화 구현 계획

> **범위:** 계획 전용. 실행 전 사용자 승인 필요.

**목표:** 영지 키마다 고정된 건축 레이아웃 유형을 선택해, 현재 팔각 로비형뿐 아니라 원형 중앙홀형과 비대칭 영주관형을 같은 실내 시스템 안에서 운용하면서 모든 상호작용·잠금문·전투·저장 기능을 유지한다.

**접근:** 씬을 영지별로 복제하지 않고 현행 단일 `IndoorScene` 및 `PlayerCastleInteriorBuilder`를 유지한다. 현재 빌더의 좌표·벽·존 판정을 하나의 레이아웃 정의로 모으고, 그 정의가 외곽/로비 형상, 방 구역, 벽과 포탈 그래프, 의미 기반 앵커 위치를 함께 제공하게 한다. 실제 `territoryKey`로 레이아웃을 결정론적으로 배정한다.

**기준 스택:** Unity 6000.4.10f1, URP, 기존 `PlayerCastleInteriorBuilder`/`IndoorSceneTransition` 구조.

---

## 확인된 현재 상태와 설계 기준

- 런타임 성 진입은 소유 여부와 무관하게 `IndoorSceneTransition`에서 `PlayerCastleInteriorBuilder.BuildPlayerCastleInterior(nation, layoutVariant)`를 호출한다. 씬을 별도로 여러 개 만들 필요는 없다.
- 현재 중앙 로비는 이름과 달리 **팔각형(8변)** 이고, 침실·제작·저장·막사·연금술·입구 구역과 실제 벽 포탈로 연결된다.
- 빌더에는 이미 `layoutVariant 0..7`이 있으나, 주된 변형은 좌우반전·기둥 수/위치·책상/장식 이동이다. 방의 형상과 토폴로지는 공통이다.
- 현재 `GetTopologyWalls()`, `GetTopologyZoneAt(point)`, `GetLobbyVertices()`, `GetAnchorPosition(name)`는 사실상 하나의 고정 레이아웃을 기준으로 한다. `TintForZone`, `InvadedLordEncounter`, 벽 장식/벽 콜라이더, `CastleInteriorBuilder.AddLordLockedDoors`, 조명/기능 앵커 등이 이 구조에 의존한다.
- 빌더의 작업대·창고·무기고·연금술·침대 등의 기능 이름과 호출 규약은 보존한다. GLB 가구 카탈로그와 플레이스홀더는 레이아웃 선택과 독립적으로 유지한다.
- 현재 변형 해시에는 실제 성 진입 키를 활용하려는 코드가 있으나, 빌더 호출은 `nation + layoutVariant`만 받으며 빌더 내부의 일부 키는 국가 스타일에서 유도된다. 배정에 사용할 **실제 영지 키 전달 여부**를 구현 전에 통합 추적하고 바로잡는다.

## 최종 레이아웃 제안

처음에는 세 가지 계열을 지원한다. 내부 구현에서 레이아웃 계열과 작은 배치 변형을 분리한다.

1. **팔각 요새형 — 기존 기준형**
   - 현행 외곽, 팔각 중앙 로비, 방 배치와 좌표를 유지한다.
   - 기존 세이브·테스트·미리보기의 기준과 롤백 대상으로 사용한다.

2. **원형 성채형 — 첫 신규 가시 차이**
   - 중앙 로비를 원형에 가까운 다각형(예: 12~16개 벽 구간)으로 바꾼다. 원은 Unity 메시/콜라이더에서 다각형으로 표현한다.
   - 외곽 치수는 현재 규모 안에 유지하고, 기능실은 로비 둘레의 방사형 포탈로 연결한다.
   - 입구는 남쪽 연결을 유지한다. 침실·저장고·제작소·막사·연금술실 연결을 실제 포탈 그래프에 각각 보존한다.

3. **비대칭 영주관형 — 방 크기·위치 차이**
   - 중심 로비를 한쪽으로 약간 이동하고 좌우 날개/방 깊이를 다르게 구성한다.
   - 비대칭은 임의 난수로 흩뜨리지 않고 각 레이아웃 정의에 기록한다. 기능실의 문·통로는 막히지 않도록 별도로 산출한다.

각 계열은 추가 소규모 가구·기둥 배치 변형을 가질 수 있지만, 구조 유형을 먼저 완성하고 시각적으로 확인한 뒤에만 확장한다. 첫 릴리스에서 3계열 전부를 반드시 동시에 켜야 하는 것은 아니며, 안전한 순서는 기준형 → 원형 → 비대칭 → 영지 배정이다.

## 핵심 계약(변경 금지)

- 영지 재방문 시 같은 영지 키는 항상 같은 레이아웃을 선택한다. `UnityEngine.Random`, 시간, 씬 진입 순서 등 전역 상태에 의존하지 않는다.
- 가능하면 같은 국가 안의 영지들도 다양한 계열을 갖게 한다. 특정 영지가 모두 같은 국가라는 이유만으로 한 유형에 고정되지 않도록 한다.
- `Workbench`, `StorageShelf_2`, `WeaponStand_0`, `AlchemyTable`, `LordBed`, `CookingTable`, `CookingIngredientWarehouse` 및 UI/세이브/전투가 찾는 기존 이름과 컴포넌트 계약을 유지한다. 앵커 좌표는 레이아웃별로 바뀔 수 있지만 올바른 기능실 안에 있어야 한다.
- 입구→로비→모든 필수 기능실 경로가 실제 문 개구부와 콜라이더에서 이어져야 한다. 그래프 정보만 연결되고 벽이 막는 불일치는 허용하지 않는다.
- 영주 성 잠금문은 의미 기반 포탈(집무실/금고/무기고/문서고)에 붙인다. 기존 `LocationId`, 난이도, 개방 대상 계약을 보존하고, 레이아웃별 포탈 이름이나 순서가 달라져도 올바른 실에 배치한다.
- 카메라/플레이어 시작점·실내 진입·퇴장 위치, 경비병 배치, 소속 깃발, 광원·포그, GLB/플레이스홀더는 새 외곽/방 배치에 맞춰 갱신한다. 천장 장식, 바닥 존 매트, AO 오버레이, 걸레받이는 다시 추가하지 않는다.
- 기존 `BuildPlayerCastleInterior(string, int)`와 고정 토폴로지 API는 테스트·미리보기 등 외부 호출자를 위해 호환 래퍼로 보존한다. 새 코드에서는 명시적인 레이아웃 정의/컨텍스트를 사용한다.

## 단계별 실행 계획

### Phase 0 — 의존성·영지 데이터 재확인 및 기준선

**목표:** 바뀌는 토폴로지 API의 모든 런타임/에디터/테스트 호출자를 확정하고 실제 영지 식별자를 기준으로 계획을 고정한다.

**대상 읽기/확인 파일:**
- `Assets/Scripts/Systems/PlayerCastleInteriorBuilder.cs`
- `Assets/Scripts/UI/IndoorSceneTransition.cs`
- `Assets/Scripts/Systems/CastleInteriorBuilder.cs`
- `Assets/Scripts/Systems/InvadedLordEncounter.cs`
- `Assets/Scripts/Systems/InteriorNationFlagSystem.cs`
- `Assets/Scripts/Systems/PlayerCastleInteriorPlaytest.cs`
- `Assets/Scripts/Tests/EditMode/PlayerCastleInteriorTopologyTests.cs`
- `Assets/Scripts/Tests/EditMode/LordCastleUnificationTests.cs`
- 에디터 실내 프리뷰 호출부(정확 경로를 검색으로 확정)
- 실제 영지 키의 원천(`TerritoryDatabase`/영지 데이터 파일)을 확인해 key 중복·국가·링 구성을 기록

**작업:**
1. `GetTopologyWalls`, `GetTopologyZoneAt`, `GetLobbyVertices`, `GetAnchorPosition`, `GetPortalConnections`의 전 호출자를 검색한다. 런타임, 에디터, 테스트 어셈블리를 모두 분류한다.
2. 성 진입 지점에서 실제 `territoryKey`가 어떻게 전달되는지 확인한다. 키가 유실되거나 국가 기본 키로 대체되는 구간을 표시한다.
3. 현재 기준형을 참조할 캡처/프리뷰 방식과 현행 테스트 기준선을 기록한다. 이 단계에서는 코드를 수정하거나 Play하지 않는다.
4. 영지 목록을 바탕으로 결정론 배정 테이블의 후보를 산출한다. 3개 계열의 비율과 인접 영지 반복 억제 정책을 명시한다.

**완료 기준:** 호출자 목록, 실제 key 출처, 기존 기능/문 계약이 확정되고 계획 밖 시스템 영향이 드러나 있지 않다.

### Phase 1 — 레이아웃 정의와 현행 팔각형 추출

**목표:** 현재 결과를 바꾸지 않으면서, 벽·존·포탈·앵커가 한 레이아웃 정의에서 나오도록 기반을 만든다.

**예상 파일:**
- 수정: `Assets/Scripts/Systems/PlayerCastleInteriorBuilder.cs`
- 신규 여부 검토: `Assets/Scripts/Systems/InteriorLayoutDefinition.cs` 및 `.meta` (공유/비교가 필요할 때만 신규)
- 테스트: `Assets/Scripts/Tests/EditMode/PlayerCastleInteriorTopologyTests.cs`

**작업:**
1. `InteriorLayoutDefinition`이 최소한 다음을 제공하도록 설계한다: 안정적인 `LayoutId`, 외곽 치수/외곽 벽, 로비 다각형, 벽 목록, 의미 기반 방 이름, 포탈 연결, 기능 앵커 배치.
2. 현행 팔각형을 `KeepOctagon` 정의로 옮긴다. 기존 벽/문 이름은 호환을 위해 가능한 한 유지한다.
3. 기존 `GetTopology...()` 메서드는 기준형 결과를 반환하는 wrapper로 둔다. 신규 오버로드/컨텍스트 기반 API는 `InteriorLayoutDefinition`을 명시적으로 받는다.
4. 정의 배열은 외부에서 수정되지 않도록 복사/읽기전용 형태로 반환한다.
5. TDD로 기준형의 벽 수·포탈 그래프·존 판정·앵커·외곽 범위가 현재 값과 동일함을 단정한다.

**검증:**
- `PlayerCastleInteriorTopologyTests`와 기존 실내 품질/잠금문 focused 테스트.
- 컴파일은 Unity QA 서브에이전트가 별도 수행. 이 단계에서는 Play 미실행.

**완료 기준:** 기존 `layoutVariant=0` 결과와 기능/벽 계약 불변. 회귀 테스트 통과 전에는 신규 형태를 추가하지 않는다.

### Phase 2 — 원형 중앙홀형

**목표:** 같은 기능실과 입구 연결을 유지하면서 중앙 로비의 실루엣이 확연히 원형으로 읽히는 레이아웃을 추가한다.

**예상 파일:**
- 수정: `Assets/Scripts/Systems/PlayerCastleInteriorBuilder.cs` 또는 Phase 1에서 분리한 레이아웃 정의 파일
- 수정: `Assets/Scripts/Tests/EditMode/PlayerCastleInteriorTopologyTests.cs`
- 조건부 수정: `Assets/Scripts/Systems/CastleInteriorBuilder.cs` (잠금 포탈의 의미 ID 연결이 분리 필요할 때)

**작업:**
1. `RoundKeep`의 로비 외벽을 12~16개 세그먼트로 구성한다. 실제 반지름·중앙 위치는 현재 로비/포탈의 공간을 기준으로 확정하며, 방과 외벽을 뚫거나 기존 보행 폭을 줄이지 않는다.
2. 기존 방을 유지하되 포탈을 원형 둘레의 의미 있는 위치에 재배치한다. 필요한 경우 두 개 연결 포탈(예: 저장/제작)을 겹치지 않는 인접 세그먼트에 둔다.
3. 새 벽 구간으로부터 충돌 메시, 상단 캡, 목재 프레임, 문틀, 경비병/영주/깃발/카메라 기준 위치를 같은 topology에서 파생한다.
4. 필수 앵커 좌표와 `GetTopologyZoneAt` 동작을 `RoundKeep` 기준으로 공급한다. 기능 위치의 하드코딩이 남지 않도록 검색 결과를 다시 확인한다.
5. 테스트: 원형 다각형 정점 수/대칭·반지름 범위, 고유 벽 이름, 실제 포탈 개구부·그래프, 외부에서 모든 기능실까지의 도달성, 앵커의 올바른 zone, 잠긴 문 배치 및 통로 폭.

**완료 기준:** 컴파일 + EditMode 통과. 사용자가 직접 볼 Play/카메라 캡처 전에는 시각 승인/전면 활성으로 간주하지 않는다.

### Phase 3 — 비대칭 영주관형

**목표:** 로비 중심과 방 날개 폭/깊이를 다르게 배치하되 기능적 연결과 가독성을 유지한다.

**예상 파일:** Phase 2와 동일한 레이아웃 정의/빌더/토폴로지 테스트 파일, 필요시 잠금문 테스트 파일.

**작업:**
1. `AsymmetricManor`의 기준 도면을 정의한다: 로비를 중심에서 약간 이동, 제작·저장 날개의 깊이/폭을 차등, 남쪽 입구 통로를 유지.
2. 비대칭 벽·포탈의 좌표를 한 정의에서 산출한다. 코드를 복사해 별도 빌더를 만들지 않는다.
3. 방별 가구/조명/명판/소속 깃발을 앵커 기준으로 배치한다. 임의 오프셋으로 벽·문·기능물에 겹치는 방식은 피한다.
4. 테스트에 비대칭 외곽 범위와 주요 공간의 비대칭성을 추가하고, 전체 포탈 연결/앵커/콜라이더 검사를 재사용한다.

**완료 기준:** 빌드·기능 계약 통과, 캡처에서 팔각형·원형과 실루엣/방 배치가 구별됨.

### Phase 4 — 실제 영지 키 기반 배정과 런타임 통합

**목표:** 각 영지가 같은 유형에 고정되지 않도록 실제 고유 키로 레이아웃을 고르고, 재방문·소유권 변화에도 예측 가능하게 유지한다.

**예상 파일:**
- 수정: `Assets/Scripts/UI/IndoorSceneTransition.cs`
- 수정: `Assets/Scripts/Systems/PlayerCastleInteriorBuilder.cs`
- 수정: `Assets/Scripts/Systems/CastleInteriorBuilder.cs` (잠금문 호출 시 레이아웃 컨텍스트 전달 필요 시)
- 수정: `Assets/Scripts/Systems/InvadedLordEncounter.cs` (침실 판정이 실제 룸/레이아웃 컨텍스트를 사용하도록)
- 수정: `Assets/Scripts/Systems/InteriorNationFlagSystem.cs` (레이아웃별 로비 앵커 위치를 받도록)
- 필요시: 경비병/플레이어 시작 위치의 관련 실내 배치 파일(Phase 0 호출자 감사 후 화이트리스트에 확정)
- 테스트: 새 `InteriorLayoutAssignmentTests.cs`(+`.meta`) 또는 기존 실내 topology 테스트

**작업:**
1. 런타임 호출에 실제 `territoryKey`를 전달하는 호환 오버로드를 추가한다. 기존 공개 빌드 시그니처는 기준형/기존 호출을 보존한다.
2. `territoryKey`에서 안정적인 해시를 계산하고 `LayoutFamily`를 할당한다. 해시 입력은 명시된 동일 규칙으로 고정한다. 플랫폼별 `string.GetHashCode()`는 사용하지 않는다.
3. 실제 영지 키 데이터로 분포를 검사한다. 국가별/링별 한 유형 쏠림과 이웃 영지의 반복을 점검하고, 필요하면 고정 배정표를 사용한다. 소유 여부만으로 성 구조가 뒤바뀌지는 않게 한다.
4. 내부 전투의 침실 판정, 영주 잠금 포탈, 깃발·가드·플레이어 배치, 조명 존 색온도는 active room이 가진 레이아웃 정의를 참조하도록 한다. 전역 가변 `ActiveLayout` 싱글턴을 두어 EditMode/다중 인테리어 빌드 상태가 서로 오염되는 설계는 금지한다.
5. 영지 키가 없을 때만 명시된 안정적 fallback(국가+소유상태 또는 기준형)을 적용하고 경고/진단 로그로 구분한다.
6. 소유권을 바꿔 재진입하는 기존 시나리오(Test_16/Test_17 포함)가 같은 영지 레이아웃을 유지하는지 검증한다.

**완료 기준:** 모든 영지에서 실제 key→레이아웃 매핑이 결정론적이며, 기능 및 소유 분기(친위대/적 수비병/잠긴 문)가 기존대로 동작한다.

### Phase 5 — 통합 회귀·미리보기 및 시각 검증 게이트

**목표:** 구조적 검증과 화면 검증을 분리해 세 유형을 비교하고, 사용자 확인 전 무리하게 메인에 확정하지 않는다.

**예상 파일:**
- 수정: `Assets/Editor/IndoorPreviewMenu.cs` (실제 경로/호출자는 검색으로 확정)
- 수정: `Assets/Scripts/Tests/EditMode/PlayerCastleInteriorTopologyTests.cs`, `LordCastleUnificationTests.cs` 및 신규 배정 테스트
- 필요시 테스트 전용 프리뷰/설정 코드 1개(실제 편집기 경로 확인 후 화이트리스트 확정)

**작업/검증:**
1. 에디터 프리뷰에서 팔각형·원형·비대칭형을 별도로 빌드·선택할 수 있게 한다. 프리뷰 호출이 런타임 레이아웃 컨텍스트와 같은 경로를 사용하도록 한다.
2. Compile, EditMode, Play 증거를 별도 보고한다. 전체 EditMode에서 기존 baseline/알려진 flaky를 구분한다.
3. **Play/스크린샷은 별도 승인 후 실행**한다. 같은 카메라 위치/줌/조명에서 3유형을 각각 캡처해 실루엣, 통로, 방 크기, 벽 막힘, 기능 가구 노출을 비교한다.
4. 실제 플레이 동선으로 입구↔로비↔침실/제작/저장/막사/연금실 이동, 침대 세이브, 제작/창고/무기고 상호작용, 영주실 잠금문, 경비병 배치/전투를 확인한다.
5. 캡처 검토 후 문제가 있으면 그 레이아웃만 수정한다. 바닥 원본/탑다운 금지 규칙을 깨는 보정은 사용하지 않는다.

**완료 기준:** 새 세 유형이 Play 화면에서 명확히 구분되고 필수 상호작용/문/동선이 확인된 후에만 적용 완료라고 보고한다.

## 위험과 대응

- **토폴로지 API가 전역 고정형:** 모든 호출자가 단일 팔각형을 암묵적으로 조회한다. → Phase 0 호출자 감사 후 레이아웃 컨텍스트 전달, 기존 API는 호환 래퍼로 남긴다.
- **영지 키가 빌더까지 전달되지 않음:** 같은 국가의 영지가 같은 형태가 될 수 있다. → 실제 key를 진입에서 빌더까지 명시적으로 보낸다.
- **기존 기능물의 절대좌표 의존:** 새 방에 벽/다른 기능물이 겹치거나 잘못된 zone으로 판정될 수 있다. → 앵커/가구/조명 위치를 의미 기반 레이아웃 정의로 이전하고 각 정의별로 검사한다.
- **원형의 다각형/문 간격 문제:** 12~16면 원형에서 포탈 폭, 벽 충돌, 문틀 중첩이 발생할 수 있다. → 포탈 구간을 우선 배정한 뒤 나머지 벽 세그먼트를 나누고 콜라이더 raycast 계약으로 검사한다.
- **지나친 범위 확장:** 완전한 레이아웃 추상화가 큰 리팩터링으로 커질 수 있다. → 기준형을 먼저 정의로 추출하고 원형 하나를 끝까지 통과시킨 뒤 비대칭형을 추가한다.
- **사용자가 원치 않는 시각 설계:** 평면 테스트만 통과하고 실물은 혼잡할 수 있다. → Play/capture 전에 확정 완료라고 하지 않고, 세 유형 캡처를 비교 가능한 게이트로 둔다.

## 승인/실행 규칙

- 본 문서는 계획만이며 소스·테스트·씬을 변경하지 않는다.
- 구현은 Phase 단위로 위임 구현자와 별도 QA 에이전트를 분리한다. 단계마다 명시 파일 화이트리스트, compile/EditMode 증거를 요구한다.
- Play와 커밋은 각각 별도 사용자 승인 게이트로 유지한다.
- 기존 dirty work를 보존하고 `git add -A`를 사용하지 않는다.
