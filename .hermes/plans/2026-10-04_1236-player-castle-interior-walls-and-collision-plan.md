# 플레이어 성 내부 벽면·입체감·플레이어 충돌 개선 계획

- 작성: 2026-10-04 12:36 KST
- 프로젝트: `/mnt/c/Unity/code` — Unity 6000.4.10f1
- 범위: 우선 플레이어 소유 성 내부(`PlayerCastleInteriorBuilder`)와 전용 검증 씬 `Test_PlayerCastleInterior`
- 모드: 계획만. 이 문서는 계획 산출물이며, 이번 단계에서는 코드·씬·에셋을 수정하거나 테스트/컴파일/Play를 실행하지 않는다.

## 목표

1. 현재 징그럽고 평면적으로 느껴지는 벽을 차분하고 설득력 있는 중세 석조 벽면으로 개선한다.
2. 벽에 닿았을 때 이동이 완전히 멈추거나 출입구를 통과하지 못하는 문제를 재현하고, 원인을 미관 수정과 분리해 찾아 고친다.
3. 방의 비대칭 형태, 방별 기능 구분, 문/통로 및 기존 상호작용 앵커·가구·조명은 보존한다.
4. 테스트 씬에서 검증한 뒤 실제 플레이어 소유 실내 진입 경로에도 결과가 같은지 확인한다. 다른 종류의 실내나 메인 씬에 의도치 않은 변경을 넣지 않는다.

## 현재 파악한 코드·검증 근거

- 실제 플레이어 소유 내부 생성은 `Assets/Scripts/Systems/PlayerCastleInteriorBuilder.cs`; 벽 면 생성은 `Assets/Scripts/Systems/IndoorBuilder.cs::CreateSolidInteriorWall`; 플레이어 이동 검증기는 `Assets/Scripts/Systems/PlayerCastleInteriorTestMovement.cs`다.
- 전용 씬 부트스트랩은 `Assets/Scripts/Systems/PlayerCastleInteriorPlaytest.cs`, 에디터 씬 생성기는 `Assets/Editor/PlayerCastleInteriorPlaytestSceneBuilder.cs`, 저장 씬은 `Assets/Scenes/TestScenes/Test_PlayerCastleInterior.unity`다.
- 벽은 두께가 있는 단일 절차 메시/`MeshCollider`로 생성되고, 문 개구부를 메시에서 잘라낸다. 현재 이동 테스트 코드는 `CharacterController.Move` 후 실내 전체 사각형 경계로만 좌표를 clamp한다. 벽·출입구를 기준으로 한 이동 회귀 테스트는 현재 계획/확인한 테스트에 없다.
- `PlayerCastleInteriorBuilder.cs`에는 현재 미커밋 변경이 있고, topology 테스트 파일도 미추적 상태다. 최신 기록의 전체 EditMode XML에는 `PlayerCastleInteriorTopologyTests` 관련 실패가 포함돼 있다(공간/개구부 계약 실패 4건). 이를 무시하거나 새 작업의 실패라고 단정하지 않고, 기존 변경 상태 및 정확한 테스트 결과를 먼저 대조한다.
- 따라서 현 단계에서는 벽이 왜 그렇게 보이는지와 이동이 막히는 원인을 확정하지 않는다. 현상별 Play 재현과 렌더/Collider 근거를 먼저 모은다.

## 작업 원칙과 보호 범위

- 작업 시작 시 `git status`, 대상 파일 diff, 현재 계획/QA 기록을 다시 확인한다. 이미 존재하는 사용자 변경을 덮어쓰거나 되돌리지 않는다. `git add -A`, reset/clean, 자동 스테이징은 금지한다.
- 먼저 시각 현상과 충돌 현상을 각각 재현한다. 벽 텍스처/메시를 바꾸면서 충돌도 한꺼번에 바꾸는 식으로 원인을 섞지 않는다.
- 플레이어 소유 성의 전용 테스트 씬과 해당 빌더를 우선 수정 범위로 삼는다. 공용 `IndoorBuilder`를 바꿔야 한다는 증거가 없으면 다른 실내 생성기에는 확장하지 않는다.
- 임의 기본 도형으로 장식물을 늘려 해결하지 않는다. 우선 벽의 메시·재질·정상맵/UV·조명과 기존 고품질 에셋 카탈로그의 재사용 가능성을 조사한다.
- 실제 화면 근거 전에는 시각 품질이나 이동 문제가 해결됐다고 선언하지 않는다. Compile, EditMode, Test Scene Play, 실제 진입 경로 확인을 서로 다른 게이트로 기록한다.

## 단계별 계획

### Phase 0 — 기준선과 재현 조건 확정

1. 대상 빌더·재질 팩토리·텍스처 생성/로드·카메라·테스트 플레이어의 현재 호출 경로와 미커밋 diff를 읽는다. 현재 동작 중인 Play Editor가 있다면 종료/전환 없이 로그·씬 상태를 먼저 조사한다.
2. 사용자가 지적한 벽이 재현되는 정확한 씬과 위치를 확인한다. 전용 `Test_PlayerCastleInterior`만의 문제인지, 플레이어가 점령한 영지의 실제 `IndoorSceneTransition` 진입에서도 나타나는지 구분한다.
3. 같은 카메라/조명/시점에서 벽의 기준 캡처를 얻는다. 벽의 색·반복 패턴·UV 스케일·표면 노멀/법선·접합선·두께/상단·그림자·벽 관통 또는 겹침을 기록한다. 외관을 “징그럽다”는 주관적 평가는 사용자의 표현으로 유지하고 원인 가설과 분리한다.
4. 이동 재현 경로를 고정한다: 평면 벽에 수직 접근, 벽을 따라 좌우 이동, 모서리 통과, 각 문 개구부 정중앙/가장자리 통과, 대각선 접근, 입구 왕복. 시작 위치·방향·입력·CharacterController 위치/크기/충돌 플래그와 해당 지점 Collider를 기록한다.
5. Scene/Game 뷰 또는 기록 가능한 Play 로그에서 벽 메시와 Collider가 같은 형상인지, 포털 가장자리/상부/인접 벽이 겹쳐 통로를 막는지, 플레이어가 벽에 닿은 뒤 접선 방향으로 미끄러지는지 완전히 고정되는지 확인한다.

**Gate 0:** 각 증상 재현이 안정적이고, 벽 외관 문제와 이동 정지의 원인이 서로 구별됐을 때만 최소 수정안을 확정한다. 미재현이면 수치를 임의 조정하지 않고 캡처/재현 정보부터 보강한다.

### Phase 1 — 벽 충돌 원인 수정 (시각 변경과 독립)

1. 관측 결과에 따라 원인을 한 항목으로 특정한다. 우선 검사 후보는 다음과 같다: CharacterController 형상·skin/step 설정과 실제 모델 위치 불일치, 벽 두께/끝면/포털 절단 메시 오류, 인접 collider 중첩 또는 숨은 기존 벽 collider 잔존, 이동 입력/좌표 경계 clamp, 경사진 면의 법선/접선 충돌이다. 후보를 사실로 간주하지 않는다.
2. 결정된 실패 사례를 재현하는 EditMode/PlayMode 테스트를 먼저 추가한다. 순수 topology 계약과 Unity 물리/CharacterController 동작 테스트를 혼동하지 않으며, 불가능한 EditMode 물리 가정을 만들지 않는다.
3. 해당 경계만 최소 수정한다. 포털 통과는 양방향·중앙 통과가 가능하고, 닫힌 벽은 통과되지 않으며, 벽을 따라 이동/모서리 회전이 막히지 않는지 확인한다. 기존 방 간 연결, 전체 외곽 차단, 바닥·천장, 상호작용 앵커는 보존한다.
4. 실패한 기존 topology 테스트의 계약을 현재 의도된 방 배치 및 실제 벽 생성 코드와 대조해 stale assertion인지 실제 오류인지 판정한다. 어느 한쪽을 증거 없이 수정해 통과시키지 않는다.

**Gate 1:** 회귀 테스트가 원인을 재현하고, 수정 후 벽 접촉·벽 타기·모서리·모든 출입구 왕복이 물리 Play에서 기대대로 동작해야 한다.

### Phase 2 — 벽 시각 방향 확정 및 메시/재질 개선

1. 기준 캡처와 사용자의 “징그럽고 입체감이 부족”하다는 피드백을 바탕으로 과한 무늬/얼룩/반복 흔적, UV 늘어짐·과도한 타일링, 법선맵 방향/세기, 평면적인 조명·재질 중 무엇이 인상을 만드는지 구분한다. 재질 입력 텍스처와 최종 렌더 결과를 둘 다 확인한다.
2. 먼저 차분한 석조 스타일을 목표로 한다: 큰 단위의 명확한 석재 분할, 절제된 색·거칠기, 자연스러운 크기 변화(규칙적 반복 억제), 벽 모서리·문설주·상단의 읽히는 깊이, 적절한 간접/측면광과 부드러운 그림자. 기존 국가색/실내 분위기를 훼손하거나 표면을 과도하게 거칠고 살덩이처럼 보이게 하는 세부 노이즈는 피한다.
3. 현재 `IndoorMaterialFactory.ApplyToTopologyWalls`와 입력 석재 텍스처/정상맵/UV 생성 및 `IndoorTextureLoader` 리소스를 확인해 재사용·보정·베이크 중 최소 위험 접근을 택한다. 실제 텍스처/정상 데이터 없이 셰이더 프로퍼티만 바꾸고 입체감이 개선됐다고 단정하지 않는다.
4. 필요한 경우에만 벽 메시의 깊이 디테일(얕은 몰딩, 문틀, 코너 마감, 석재 단차)을 설계한다. 실루엣·방 크기·걸을 수 있는 공간은 유지하고, 장식의 Collider는 불필요한 이동 장애물이 되지 않도록 분리한다.
5. 매 변경은 동일 카메라·조명·해상도의 비교 캡처로 검토한다. 과한 강조나 벽 패턴이 반복되면 다음 시도 전에 어떤 입력/표현이 원인인지 다시 좁힌다.

**Gate 2:** 사용자 기준으로 벽이 보기 편하고 석조 표면/두께/문설주가 읽히며, 평면감이 줄었다는 실제 Play 캡처가 있어야 한다.

### Phase 3 — 통합 회귀와 수용 검증

1. 작업 중 TDD 순서에 맞춰 대상 테스트와 관련 기존 테스트를 실행하고, Unity batch compile 결과를 최신 소스 시각과 일치시킨다.
2. 최신 전체 EditMode 결과와 실패별 사유를 기록하고 기존 baseline과 비교한다. 기존 실패가 남아 있으면 전체 성공이라고 표현하지 않는다.
3. 전용 테스트 씬에서 모든 이동 경로, 벽 외관, 문 개구부, 방별 진입, 가구·상호작용 앵커·조명/카메라를 Play로 확인한다.
4. 가능하면 실제 플레이어 소유 성 진입 경로에서도 같은 벽 재질과 이동 동작을 확인해 테스트 씬 전용 구현으로 끝나지 않았음을 검증한다. MainScene 및 다른 실내의 영향은 변경 범위와 실제 call path를 기준으로 확인한다.
5. `QAPROGRESS.md`와 `ROADMAP.md`에는 계획·구현·검증 게이트를 구분해 기록한다. 완료 처리는 실제 수용 기준을 만족한 항목에만 한다. 이 계획 요청만으로는 코드 수정·커밋·푸시를 하지 않는다.

## 수용 기준

- 벽 패턴이 과도하게 혐오감을 주거나 반복/늘어짐으로 산만하지 않고, 돌벽의 두께·문틀·표면 변화가 자연스럽게 읽힌다.
- 플레이어는 벽에 닿았을 때 진행 방향이 막히더라도 벽을 따라 이동하고 모서리를 돌아 나올 수 있으며, 설계된 문과 입구를 통과한다.
- 막힌 벽은 막힌 상태를 유지하고 방 외곽으로 빠져나가지 않는다. 숨은 collider/겹친 벽이 문 개구부를 봉쇄하지 않는다.
- 방 구조, 비대칭 공간 구성, 기존 상호작용 대상/앵커, 플레이어 성 기능은 보존된다.
- Compile/EditMode/Play 결과를 분리 기록하고, 실제 캡처와 테스트가 없는 항목을 완료라고 하지 않는다.

## 위험·열린 사항

- “벽면”이 플레이어 소유 성 내부가 아닌 다른 실내를 가리키는 경우 수정 대상이 달라질 수 있다. 첫 재현에서 실제 씬/벽을 확인하고, 범위가 다르면 구현 전에 계획을 갱신한다.
- 최신 topology 코드는 이미 미커밋이고 이전 테스트 결과에 topology 실패가 있어, 새로운 변경을 기존 변경과 섞어 원인을 오판할 위험이 있다. 작업 시작 때 현재 diff와 테스트 기준선을 먼저 고정한다.
- 임시 플레이테스트의 단순 캡슐 캐릭터와 실제 플레이어의 크기·회전·이동 구현이 다르면 재현 결과가 달라질 수 있다. 전용 씬 수용 후 실제 진입 플레이어도 별도 확인한다.
- 사용자 기준의 구체적 벽 재질/참조 이미지는 아직 제공되지 않았다. 우선 현재 벽을 과장 없이 개선하는 방향으로 비교안을 만들되, 특정 역사 양식/색상 고정은 실제 캡처나 추가 요청 없이 임의 확정하지 않는다.

## 추가 범위 — 실내 기능 오브젝트 상호작용 배선

사용자 후속 요구: 실내의 크래프트·병사 배치 등을 포함해 놓여 있는 모든 기능 오브젝트를 실제 플레이에서 상호작용 가능하게 배선한다. 이를 벽 미관/충돌 작업과 별도의 검증 가능한 트랙으로 포함한다.

### 코드에서 확인된 현재 상태

- 이미 컴포넌트가 붙는 경로: `Workbench`의 `TerritoryCraftingStation`, `StorageShelf_2`의 `TerritoryWarehouse`, `WeaponStand_0`의 무기고용 `TerritoryWarehouse`, `CookingTable`의 `CookingStation`, `AlchemyTable`의 `AlchemyStation`, `LordBed`의 `Bed`(가구 카탈로그에서 trigger collider와 함께 추가).
- 주의: `TerritoryCraftingStation`, `TerritoryWarehouse`, `CookingStation`, `AlchemyStation`은 각자 E키를 폴링한다. 근접 반경이 겹치면 같은 키 입력에 여러 스테이션이 반응할 수 있다. 게임 입력 설정은 Input System과 구 Input Manager를 모두 허용하지만, 테스트 씬이 실제 `PlayerMovement`/전역 UI 초기화까지 보장하는지는 별도 확인해야 한다.
- 병사 배치실은 현재 남동쪽 방/조명과 관련 가구가 있을 뿐, `PlayerCastleInteriorBuilder`에서 병사 배치/관리 상호작용 컴포넌트를 붙이는 호출은 확인되지 않았다. 재사용 가능한 화면은 `SoldierManagementUTK.Open()` 및 `TerritoryDeploymentUTK.Open()`이 있고, `TerritoryDeploymentSystem`과 `GuardTaskSystem`이 역할/배치 로직을 제공한다. 어떤 화면/API가 해당 실내 기능에 맞는지 확인 후 연결한다.
- 기존 플레이어 E 상호작용 경로(`PlayerMovement.HandleInteraction`)는 현재 Bed를 먼저 찾아 호출하는 구현을 포함한다. 건물 스테이션의 독립 E 폴링과 충돌/중복을 포함해 실제 입력 소유권을 추적한다.

### 배선 단계

1. 방별 기능 목록과 현재 런타임 오브젝트/컴포넌트/UI/API를 행렬로 작성한다: 작업대(장비 제작·수리), 요리, 연금, 저장고, 무기고, 침대(수면·세이브), 병사 배치/관리, 그리고 기능 오브젝트처럼 보이는 기타 배치물. 장식물은 기능이 없는 것으로 명시해 누락과 의도적 비상호작용을 구분한다.
2. 각 항목의 전체 호출 경로를 따라간다: 가까이 접근 → 프롬프트 → 입력 한 번 소비 → 대상 판별 → UI 열기/시스템 API 실행 → 닫기/취소 → 입력 재개. 미구현 UI와 단순히 기존 UI 진입선이 빠진 경우를 구분한다.
3. 먼저 겹치는 거리에서 E키가 중복으로 소비되는지 및 테스트 씬의 UI Root/Player/UIManager/Core systems 존재 여부를 재현한다. 필요할 때만 공용 근접 상호작용 라우터를 설계하며, 구현 시 한 번의 입력당 가장 가까운 상호작용 대상 하나만 실행하는 방식과 기존 단독 상호작용의 호환성을 회귀 테스트로 고정한다.
4. 병사 배치 지점은 기존 병사 명부/영지 배치 UTK와 실측 시스템을 재사용하는 전용 상호작용 진입선으로 배선한다. 단순 프롬프트만 추가하지 말고 플레이어 소유 영지 ID/상태 전달, UI 표시, 역할 할당/변경/해제 결과까지 확인한다. 기존 UI가 해당 성 내부에서 필요한 기능을 제공하지 않는 것이 확인될 경우에만 구체적 누락을 새 작업 범위로 제시한다.
5. 각 스테이션/시스템에 대해 API 수준의 테스트(대상 구성, 영지 ID, 올바른 UI 진입, 입력 단일 소비, 권한/거리 경계)를 추가한다. Unity 입력/렌더/실제 UI 동작은 Play 테스트에서 따로 확인한다.
6. 이 배선 트랙은 벽 충돌 및 시각 변경과 변경 단위·테스트를 분리한 뒤 통합 회귀한다. 모든 방/각 앵커를 순회하는 체크리스트를 사용해 미연결/중복 연결을 확인한다.

### 배선 수용 기준

- 크래프트, 요리, 연금, 일반 창고, 무기고, 침대, 병사 배치/관리가 각자의 기대 동작으로 연결되며 올바른 영지/데이터를 사용한다.
- 한 번의 상호작용 입력으로 가까운 대상 하나만 실행된다. 겹친 거리에서 다른 스테이션 UI가 함께 열리거나 UI 없는 단순 로그로 끝나지 않는다.
- 표시 프롬프트와 실제 사용 가능 거리/키가 일치하고, UI가 없거나 시스템 초기화가 안 된 경우 명확한 진단을 제공한다.
- 기존 전역/다른 실내의 상호작용과 UI 호출을 회귀시키지 않는다. 장식 소품을 상호작용 가능하다고 오인하지 않도록 기능 오브젝트 인벤토리를 문서화한다.
